> идут по Рабочей документации (РД), поэтому Мастер-список строится по РД. Рабочая область
> объекта состоит из шифров РД (ТСО, КЖ, ЭМ, …; в т.ч. «30 крановых узлов» — набор шифров

1. Назначение системы
Веб-приложение для отдела ПТО, позволяющее:

Собирать данные из комплектов Рабочей документации (шифров РД) объекта в единый Мастер-список.

Контролировать полноту и консистентность позиций РД между шифрами объекта.

Контролировать наличие и привязку документов (паспорта, сертификаты, акты) к каждой позиции.

Формировать акты (АВК, АОСР, ВСО, ВР) с автоматической подстановкой документов.

Визуализировать статус закрытия объекта ("Контрольная таблица").

1.1. Глоссарий
ПТО — производственно-технический отдел.
РД — рабочая документация (спецификации, схемы).
Шифр РД — раздел рабочей области объекта (ТСО, КЖ, ЭМ и др.). Шифров в объекте может быть много; часто это «системные» шифры, но бывает и «30 крановых узлов», внутри каждого свои ТСО/КЖ/ЭМ.
Смета — сметная документация (объёмы и стоимость работ/материалов). В MVP не участвует.
Мастер-список — единый список позиций (материал / оборудование / работа), собранный из РД всех шифров объекта; строки остаются в своих шифрах и помечаются колонкой «Шифр». Объединение одинаковых позиций из разных шифров — ручное действие (позже), единая истина по объекту.
АВК — акт входного контроля (оформляется на материалы и оборудование при поступлении).
АОСР — акт освидетельствования скрытых работ (РД-11-02-2006); оформляется на работы, которые требуется предъявить до их закрытия (например, кабель в траншее до обратной засыпки). В АОСР дополнительно фигурируют связанные материалы и номера актов АВК. В Контрольной таблице закрытие АОСР учитывается у позиций типа «материал» (см. матрицу в 3.5).
ВСО — ведомость смонтированного оборудования также с номерами актов АВК.
ВР — ведомость выполненных работ.
Ключевой принцип: каждая позиция Мастер-списка (материал, оборудование или работа) должна быть закрыта хотя бы одним из перечисленных документов; распределение позиций по актам выполняет инженер вручную.

2. Ролевая модель
Роль	Права
Руководитель ПТО	Создает объекты, назначает инженеров, видит дашборды по всем объектам.
Инженер ПТО	Работает только с назначенными объектами.
Администратор	Управление компаниями и пользователями (опционально).
3. Функциональные требования
3.1. Управление объектами и доступом
Руководитель ПТО создает объект (название, шифр объекта, даты).

Внутри объекта ведётся рабочая область из шифров РД. Шифры добавляются по мере поступления документации и ничем не ограничены: системные (ТСО, КЖ, ЭМ, …) и «узловые» (например, 30 крановых узлов — набор шифров в каждом узле).

Назначает инженеров на объект через интерфейс.

Инженер видит и работает только с теми объектами, куда назначен.

Дашборд руководителя: сводка по всем объектам (% готовности, красные позиции, риски).

3.2. Загрузка и нормализация данных РД
Загрузка файлов .pdf / .xlsx (спецификации РД). Файл привязывается к шифру объекта.

Парсинг структурированных данных для PDF с текстовым слоем: номера позиций, названия, марка/ТУ, код, поставщик, единицы измерения, количество. Для сканов-спецификаций — полуручной режим (OCR в MVP не для спецификаций).

Определение типа позиции (материал / оборудование / работа) — автоматически по словарям, с ручной корректировкой. Тип влияет на то, какими актами позиция закрывается.

Сохранение в БД с привязкой к объекту и шифру.

3.3. Рабочая область РД и Мастер-список
Рабочая область объекта — разделы-шифры (ТСО, КЖ, ЭМ и т.д.). В раздел загружаются спецификации, из них извлекаются позиции.

Мастер-список = позиции РД всех шифров объекта, единое окно для контроля документов. Каждая строка остаётся в своём шифре и имеет колонку «Шифр»; доступны фильтры по шифру и поиск.

Одинаковая позиция в разных шифрах — раздельные строки. Система помечает такие строки как «возможные дубли» (подсветка); объединение в одну мастер-позицию — ручное действие, планируется отдельной задачей.

Позиции хранятся «как в документе»; инженер может править их вручную. В будущих версиях: сведение со сметой, сверка объёмов, авто-объединение дублей между шифрами.

3.4. Пул документов (паспорта, сертификаты)
Загрузка ZIP-архивов с PDF-паспортами (или поштучно). Для цифровых PDF (есть текстовый слой) текст извлекается напрямую, OCR применяется только к сканам.

OCR-распознавание в фоне (Celery): номер документа, дата, завод-изготовитель, марка.

Связь «паспорт ↔ позиция» — многие-ко-многим: один паспорт (партия материала) может закрывать несколько позиций Мастер-списка, и у одной позиции может быть несколько паспортов.

Библиотека документов с поиском по номеру и названию.

3.5. Контрольная таблица (статусы закрытия)
Таблица: Мастер-список (строки) × Типы закрывающих документов (столбцы):

Паспорт/Сертификат

Акт входного контроля (АВК)

АОСР

Ведомость смонтированного оборудования (ВСО)

Ведомость выполненных работ (ВР)

Матрица закрытия (решение заказчика; определяет, какие ячейки нужны, а какие серые):

| Тип позиции | Паспорт/Сертификат | АВК | АОСР | ВСО | ВР |
|---|---|---|---|---|---|
| Материал | требуется | требуется | требуется | не требуется | не требуется |
| Оборудование | требуется | требуется | не требуется | требуется | не требуется |
| Работа | не требуется | не требуется | не требуется | не требуется | требуется |

Статусы ячеек:

🟢 Зеленый — готово.

🟡 Желтый — в процессе (черновик).

🔴 Красный — отсутствует (критично).

⚪ Серый — не требуется (проставляется по типу позиции согласно матрице выше; инженер может переопределить тип позиции вручную). Если тип не определён, ячейки АОСР/ВСО/ВР помечаются «?» до классификации.

Фильтры: по статусу, по типу позиции (материал/оборудование/работа), по типу работ, по дате.

3.6. Конструктор актов (генерация)
Создание акта с выбором типа: АВК / АОСР / ВСО / ВР.

Выбор позиций из Мастер-списка (через галочки).

Умный фильтр по типу позиции: АВК предлагает материалы и оборудование; АОСР — материалы; ВСО — оборудование; ВР — работы. Позиции с неопределённым типом предлагаются только в АВК/АОСР/ВСО. Подсветка позиций, для которых уже есть паспорта/сертификаты.

Привязка документов к позициям (выпадающий список).

Генерация .docx-файла по шаблону с заполненным актом и приложениями (паспортами).

3.7. Раннее предупреждение (прогноз рисков)
Инженер выбирает дату плановой сдачи (например, АОСР через 3 дня).

Система сканирует Мастер-список и выдает список позиций, по которым нет паспортов или актов.

Экспорт отчетов в Excel.

4. Технический стек
Компонент	Технология
Бэкенд	FastAPI (Python 3.11+), SQLAlchemy 2, Alembic
База данных	PostgreSQL (с JSONB)
Очередь задач	Celery + Redis
Хранилище файлов	MinIO (S3-совместимое, в Docker Compose); presigned-ссылки; квота ~10 ГБ на объект
Фронтенд	React / Next.js (таблицы, модалки, дашборды)
OCR	PaddleOCR (сканы, в контейнере); для цифровых PDF — извлечение текста без OCR
Генерация DOCX	docxtpl (шаблоны .docx + подстановка данных)
Инфраструктура	Docker Compose
Аутентификация	JWT (email + пароль)
5. Структура базы данных (ключевые сущности)
text
Company (компания)
  └── User (пользователь: роль, email, ФИО)
        └── ConstructionObject (объект: название, шифр, даты, статус)
              ├── ObjectAssignment (назначение: инженер → объект)
              ├── RdSection (шифр РД: ТСО/КЖ/ЭМ/…, сортировка)
              │     └── ObjectFile (загруженный файл: спецификация, паспорта; привязка к шифру)
              │           └── SourceItem (сырая позиция РД из файла)
              ├── Nomenclature (Мастер-список: позиции РД всех шифров; тип: материал/оборудование/работа; колонка «Шифр»)
              │     └── NomenclatureDoc (связь позиция ↔ паспорт, многие-ко-многим)
              ├── IncomingDoc (паспорт/сертификат: файл в S3, распознанные поля)
              ├── Act (акт: тип [АВК/АОСР/ВСО/ВР], статус, дата)
              │     └── ActItem (связь: акт → позиция из Мастер-списка)
              └── (Сметы, конфликт-детектор РД↔Смета — будущие версии, вне MVP)
6. Безопасность и изоляция
Все запросы к API проверяют доступ пользователя к объекту (Middleware/FastAPI Dependency).

Инженер видит только свои объекты.

Руководитель видит все объекты своей компании.

Данные разных компаний полностью изолированы (company_id). В MVP закладывается только фундамент (поле company_id и проверки доступа); мультитенантный UI и администрирование компаний не разрабатываются и не тестируются в рамках MVP.

7. Ограничения MVP
Ограничение	Комментарий
Шаблоны актов	4 жёстко зашитых шаблона (АВК, АОСР, ВСО, ВР). Без редактора.
Форматы файлов	На вход: .xlsx / .pdf (спецификации РД), .pdf / .zip (паспорта). На выход: .docx.
Сметы	Вне MVP: сметные данные, XML АРПС и сведение РД↔Смета не реализуются.
Лимиты файлов	PDF поштучно до 100 МБ (безопасное значение по умолчанию, настраивается); ZIP-архив паспортов до 1 ГБ (реальные сканы достигают 600 МБ); квота хранилища 10 ГБ на объект; очистка хранилища — ответственность пользователя.
ЭЦП	Не реализуется. Акт = черновик для печати.
Количество позиций	До 1000 на объект (на шифр).
OCR	Распознаёт ключевые поля (номер, дата, завод-изготовитель, марка); не обязателен для работы; для цифровых PDF не требуется. Спецификации-сканы — полуручной режим.
PDF-спецификации	Парсинг PDF-спецификаций (текстовый слой) реализован; точность растёт с образцами.
Шифры РД	Рабочая область объекта не ограничена по числу шифров (системные и узловые наборы).
Компании	Мультитенантный UI вне MVP; изоляция по company_id закладывается в модели данных.
8. Критерии приемки (DoD)
□ Руководитель создает объект и назначает инженера.
□ Инженер видит объект в своем списке.
□ Инженер заводит шифры рабочей области объекта и загружает спецификации РД в нужные шифры.
□ Мастер-список показывает позиции РД всех шифров с колонкой «Шифр» и фильтрами.
□ Инженер создает Мастер-список через выпадающие списки.
□ Инженер загружает паспорта — система распознает номера/даты.
□ Инженер создает акт, выбирает позиции, подставляет паспорта.
□ Система генерирует валидный .docx-файл.
□ Инженер открывает Контрольную таблицу и видит цветные статусы.
□ Инженер выгружает отчет «Отсутствующие паспорта» в Excel.
□ Руководитель видит дашборд по всем объектам.
□ Все данные изолированы между объектами и компаниями.
