# Спринт 0–1. Каркас проекта + ролевая модель, объекты, назначения

> Статус: план (черновик). Дата: 09.09.2026. Репозиторий: `StroyDoc`.
> Базовый документ: `README.md` (ТЗ v1.0). Оценка: **5–7 рабочих дней** для команды из 2 разработчиков (бэкенд + фронтенд).

## 1. Цель спринта

Создать фундамент продукта и закрыть первую сквозную бизнес-функцию:

1. Рабочий каркас проекта (монорепо, Docker Compose, БД, MinIO, CI) — Спринт 0.
2. Авторизация (JWT) + ролевая модель (Администратор / Руководитель ПТО / Инженер ПТО).
3. CRUD объектов строительства и назначение инженеров на объекты.
4. Изоляция доступа: инженер видит только назначенные объекты, руководитель — все объекты компании.
5. Обновлённое ТЗ зафиксировано в репозитории (коммит в `main`).

## 2. Предположения

| № | Предположение |
|---|---------------|

| 5 | Роль «Администратор» в MVP = суперпользователь своей компании (управляет пользователями); UI управления компаниями не делаем. |

## 3. Объём спринта

### В скоупе

## 4. Макет API (`/api/v1`)

### Auth
| Метод | Путь | Кто | Назначение |
|-------|------|-----|-----------|
| POST | `/auth/login` | все | `{email, password}` → `{access_token, user}` + httpOnly cookie с refresh |
| POST | `/auth/refresh` | все (cookie) | обновление access-токена |
| POST | `/auth/logout` | авторизован | очистка cookie |
| GET  | `/auth/me` | авторизован | текущий пользователь + роль |

### Users
| Метод | Путь | Кто | Назначение |
|-------|------|-----|-----------|
| GET  | `/users` | Руководитель/Админ | список пользователей компании |
| POST | `/users` | Руководитель/Админ | создать пользователя (email, ФИО, роль) |
| PATCH | `/users/{id}` | Руководитель/Админ | изменить ФИО/роль/активность |
| POST | `/users/{id}/reset-password` | Руководитель/Админ | сброс пароля (временный пароль) |

### Objects
| Метод | Путь | Кто | Назначение |
|-------|------|-----|-----------|
| GET  | `/objects` | все роли | список с учётом доступа (инженер — только назначенные) |
| POST | `/objects` | Руководитель/Админ | создать объект (название, шифр, даты) |
| GET  | `/objects/{id}` | с доступом к объекту | карточка объекта |
| PATCH | `/objects/{id}` | Руководитель/Админ | изменить объект |
| GET  | `/objects/{id}/assignments` | с доступом | список назначенных инженеров |
| POST | `/objects/{id}/assignments` | Руководитель/Админ | назначить инженера |
| DELETE | `/objects/{id}/assignments/{user_id}` | Руководитель/Админ | снять назначение |

### Политики доступа (реализуются FastAPI-зависимостями)
- Инженер видит объект только при наличии записи `ObjectAssignment`.
- Руководитель/Админ видят все объекты своей компании.
- Любой запрос к чужому объекту/другой компании → **403**.
- Токен содержит `user_id`, `company_id`, `role`; объект всегда проверяется в границах `company_id`.

## 5. Модель данных (первая миграция Alembic)

```
company            id, name, created_at
user               id, company_id FK, email, password_hash, full_name,
                   role [admin | pto_head | pto_engineer], is_active, timestamps
                   UNIQUE (company_id, email)
construction_object id, company_id FK, name, code (шифр),
                   start_date, end_date, status [planning|active|closed], timestamps
object_assignment  id, object_id FK, user_id FK, created_by, created_at
                   UNIQUE (object_id, user_id)
```

- Инженер = пользователь с ролью `pto_engineer`, назначенный на объект.
- «Руководитель ПТО» = `pto_head`. «Администратор» = `admin`.
- Каскады: удаление компании → пользователи/объекты; удаление пользователя → назначения.
- Enum ролей/статусов — PostgreSQL enum или varchar + CHECK (решение на код-ревью).

## 7. Definition of Done (приёмочные сценарии)

Выполнены все, запуск — одной командой `docker compose up`, автотесты зелёные:

- [ ] Админ логинится, создаёт пользователя-инженера и объект (название, шифр, даты).
- [ ] Админ назначает инженера на объект через UI.
- [ ] Инженер логинится и видит в списке только назначенный объект.
- [ ] Инженер получает **403** при запросе чужого объекта (проверено автотестом).
- [ ] Руководитель ПТО видит все объекты компании.
- [ ] Инженер не видит разделов «Пользователи» и «Создать объект» (ролевой guard на UI и API).
- [ ] `POST /auth/refresh` продлевает сессию; протухший/битый access → 401; logout инвалидирует refresh.
- [ ] Swagger `/docs` доступен; все эндпоинты документированы.
- [ ] Автотесты API покрывают auth + изоляцию + CRUD; CI зелёный на PR.
- [ ] MinIO поднят, health-чек проходит (задел под Спринт 2).
- [ ] ТЗ (README) и план спринта закоммичены в `main`.
